# Braintree for Craft Commerce 3.1.2

> **Status:** built - **Version:** 0.2
> The gateway settings page opens on Craft 4 again, a template can set any drop-in option the
> plugin hardcodes, and the CP payment modal is checked against Commerce 4 and 5.

---

## 1. How it works

The gateway settings page lists each site in the per-currency Site Overrides table, headed by
the site's label: `getUiLabel()` on Craft 5, the site's name on Craft 4.

The front-end drop-in builds its options as it does now (card, vault, PayPal, Apple Pay,
Google Pay, 3-D Secure, translations), then lays a template-supplied `dropinOptions` object over
them with a deep merge before calling `braintree.dropin.create()`:

```twig
{{ gateway.getPaymentFormHtml({
    dropinOptions: {
        card: { overrides: { fields: { cvv: { placeholder: 'CVV' } } } },
        paypal: null,
    },
}) }}
```

The CP "Make payment" modal renders hosted fields (not the drop-in). Commerce 4 and 5 build the
modal once per page and only `show()` it on later opens (`CommerceOrderEdit.js:32-40`), so the
hosted-field iframes are never torn down and rebuilt.

## 2. Scope

**In:** #58 (Craft 4 settings crash), #60 (template `dropinOptions`), #41 (retest; a guard only
if the modal is dead on reopen). README, CHANGELOG.

**Out:** `dropinOptions` from a config file (#60's second ask; Sam's decision of 20 Oct 2026 is
the template only). JavaScript functions in `dropinOptions` (JSON cannot carry them; the
existing `callbacks` param stays the way in). Payment sources (#53). Any GitHub comment, push
or tag.

## 3. User journeys

1. A Craft 4.15 / Commerce 4.8 store upgrades to 3.1.2 and opens Commerce → Gateways →
   Braintree. The page renders; each site's row is headed by its name.
2. A store whose customers mistake the CVV placeholder for an entered value passes
   `dropinOptions: {card: {overrides: {fields: {cvv: {placeholder: ''}}}}}` and the CVV field
   shows no dots. Every other default (cardholder name required, vaulting, PayPal) is kept.
3. A store that does not take PayPal passes `dropinOptions: {paypal: null}`; the drop-in shows
   no PayPal option.
4. An admin opens an order, clicks Make payment, cancels, clicks Make payment again, and types
   a card: the fields respond.

## 4. Data model

None. No setting, table or project config changes.

## 5. Rules

- **BR-1** The Site Overrides heading is `site.name|t('site')`, which is what Craft 5's
  `Site::getUiLabel()` returns, on both versions. Not `site.uiLabel ?? site.name`: a Yii object's
  `__call` makes Twig's defined-test pass, so the fetch still throws on Craft 4. The template
  uses no Twig syntax newer than Craft 4.0's: the hash spread (Twig 3.7) becomes `|merge`, and
  `collect().keyBy(arrow).map(arrow)` (method-argument arrows, Twig 3.7) becomes a `for` loop.
- **BR-2** `dropinOptions` is read only when it is a non-empty hash; it reaches the page as
  JSON in a `data-dropin-options` attribute on the drop-in container.
- **BR-3** The merge is deep for plain objects; an array, a string, a number or a boolean
  replaces the default outright; `null` removes the option.
- **BR-4** `authorization` and `container` are always the plugin's; `dropinOptions` cannot
  change them.
- **BR-5** The merge runs after every default is set, translations included, so a template can
  override anything else the plugin sets.
- **BR-6** Invalid JSON in the attribute is logged to the console and ignored; the drop-in
  still loads with the defaults.
- **BR-7** (#41) A guard against double initialisation is added only if the modal is shown to
  be dead on reopen on Commerce 4 or 5.

# Appendix B - build scaffolding

## B1. Before writing anything

No site may be broken by the upgrade: a template that passes no `dropinOptions` gets exactly the
drop-in it gets today.

## B2. Context to load

1. `src/gateways/Gateway.php` `getSitePaymentFormHtml()` (1058): params pass straight through
   to the template, so `dropinOptions` needs no PHP.
2. Commerce `web/assets/commercecp/src/js/CommerceOrderEdit.js` (32) and
   `CommercePaymentModal.js`: the modal is built once, re-shown after.

## B3. Guardrails

- **Do not let `dropinOptions` replace `authorization` or `container`.**
- **Do not change the hosted-fields JS unless TS-5 fails.**

## B4. Definition of done

- [ ] TS-1 to TS-4 pass; TS-5 run or reported as blocked with its reason
- [ ] README documents `dropinOptions`; CHANGELOG has 3.1.2; committed, not pushed or tagged
